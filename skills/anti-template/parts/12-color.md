# 12 — Color

Read when: choosing or reviewing colours, writing tokens, adding a dark theme, colouring status, badges, charts or maps, or when a design "looks AI" and nobody can say why. Nine times out of ten the palette is the reason.

Guidance: DESIGN.md and the brief override this part.

Fixes never name a brand hex. They name the token from DESIGN.md. If DESIGN.md has no palette yet, stop and ask for one or build a neutral-first set and flag it in the handoff.

## 12.1 AI default palettes

These colours are Tailwind and shadcn defaults and the colours models reach for when nobody chose. Seeing them in a client project without DESIGN.md asking for them is a tell.

```
#6366f1 (indigo-500), #4f46e5 (indigo-600), #818cf8 (indigo-400), #8b5cf6 (violet-500), #7c3aed (violet-600), #a855f7 (purple-500), #9333ea (purple-600), #ec4899 (pink-500), #d946ef (fuchsia-500), #667eea → #764ba2 (the classic gradient), #06b6d4 / #22d3ee (cyan) on #000, #10b981 (emerald-500) with zinc grays, #3b82f6 / #2563eb (blue-500/600 default primary), #0ea5e9 (sky), #f97316 → #ec4899 (sunset gradient), #14b8a6 → #3b82f6 (teal to blue), #0f172a (slate-900) + #6366f1, #18181b (zinc-900) + #fafafa, #1e1b4b (indigo-950 "space" background), #00ff88 / #39ff14 (neon green)
```

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Indigo or violet primary (`#6366f1`, `#8b5cf6`) | The most common AI default | `var(--color-primary)` from DESIGN.md |
| Slate-900 background with indigo accent | Default "modern SaaS" dark look | DESIGN.md palette; light theme default unless the client asks for dark |
| Emerald accent on zinc grays | shadcn/Vercel-adjacent default | DESIGN.md accent |
| Purple → pink gradient on buttons, headings, badges | The Tailwind AI gradient | Solid `var(--color-primary)` |
| `#667eea → #764ba2` | Copied from 2016 gradient sites into every model's memory | Solid colour |
| Cyan or neon green on black ("hacker" look) | Crypto and dev-tool cliché | DESIGN.md palette; muted, accessible accent |
| Blue-600 primary with no reason | Default Tailwind/Bootstrap blue | DESIGN.md primary. If the client's brand is blue, use their blue |
| Deep indigo "space" backgrounds (`#1e1b4b`, `#0f0a2e`) | AI product look | Neutral surface tokens |
| Rainbow feature icons (blue, green, purple, orange, pink, one per card) | Colour as decoration | One neutral icon colour |
| Pastel card fills per category (mint, lavender, peach) | Dribbble look | Neutral surfaces; category shown by text label |
| Tailwind palette names in code (`bg-indigo-600`, `text-slate-500`) | Palette leaks into components | Role-named theme colours mapped to DESIGN.md (`bg-primary`, `text-muted`) |
| Palette generated by a tool with 10 shades × 8 hues, all used | Colour sprawl | Primitives kept in one file; components use 10–15 semantic tokens |

## 12.2 How many colours

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| 5+ accent colours on one screen | Chaos; nothing stands out | One accent per viewport. Everything else neutral or status |
| Accent used for headings, links, icons, borders, badges and buttons at once | Accent loses its job | Accent for the primary action, active nav item, links and focus only |
| Secondary and tertiary brand colours used as decoration | Colour for its own sake | Secondary colours only where DESIGN.md assigns a role |
| Every section a different background tint | Alternating band template | One page background, one surface colour |
| Colour-coded sidebar items (each nav link its own colour) | Decoration | One highlight colour for the active item |
| Coloured dividers between sidebar groups | Noise | One border token |
| Colour used to make things "pop" | No meaning | Size, weight, position or whitespace for emphasis; colour for meaning |

A working product needs roughly: 1 accent (plus its hover and subtle tint), 6–9 neutrals (bg, surface, surface-alt, border, border-strong, text, text-muted, text-subtle, overlay), and 4 status colours (success, warning, danger, info), each with a text colour and a subtle background. That is 20–25 semantic tokens. If a project has 60, most are unused or duplicates.

## 12.3 Neutrals, black and white

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Pure black `#000` page background | Harsh; smears on OLED when scrolling; the "Vercel hero" look | Near-black dark surface token from DESIGN.md (the original rule named #111, #1a1a1a, #18181b as typical ranges) |
| Pure white `#fff` text on near-black | Glare and halation for long reading | Off-white text token on dark surfaces (the original rule named #e5e5e5 on #1a1a1a as a typical pair) |
| Pure black `#000` body text on white | Slightly harsh for long text | Dark neutral text token; contrast still well above 7:1 |
| Grays tinted blue or purple by default (Tailwind slate, "cool gray" with indigo) | Signals the default kit | Neutrals that match DESIGN.md: true grays, or grays tinted toward the brand hue on purpose |
| Tinted page backgrounds (light lavender, mint, cream) with no brand reason | Template feel | Clean neutral or the DESIGN.md background |
| 15 grays in use (`gray-50` through `gray-900` plus `slate` and `zinc`) | Mixed kits | One gray ramp. Semantic tokens pick from it |
| Borders darker than text | Heavy grid; text recedes | Border contrast lower than text; around 1.3–1.5:1 against the surface for dividers, 3:1 for input borders |
| Surfaces indistinguishable (card = page = header) | No structure | Page and surface differ by a visible step, or cards use a border |
| Very light gray text (`#9ca3af` on white) for body copy | Fails 4.5:1 | `var(--color-text-muted)` checked at 4.5:1 |

## 12.4 Contrast

WCAG 2.2 targets: 4.5:1 for normal text, 3:1 for large text (24px regular or 18.66px bold and up), 3:1 for UI component boundaries and focus indicators, 3:1 for meaningful graphics such as chart lines and icons without text. Disabled controls are exempt, but still need to look disabled.

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Gray text on gray surface (muted text on `surface-alt`) | Passes on white, fails on the tinted panel | Check each muted text token against every surface it sits on |
| Placeholder text at 2:1 | Unreadable; users think the field is filled | Placeholder at 4.5:1 if it carries information. Better: put the info in a label or helper text. See part 17 |
| Helper and caption text at 12px and low contrast | Two problems at once | 14px minimum, 4.5:1 |
| White text on a light brand colour (yellow, light green, sky) | Fails contrast | Dark text on light brand fills; define `--color-on-primary` per brand colour |
| White text on a mid-tone button with `opacity: 0.9` hover | Hover drops below 4.5:1 | Hover token that keeps contrast |
| Text on photos with no scrim | Contrast varies across the image | Text beside the image, or a flat scrim tested against the lightest area |
| Gradient behind text | Contrast changes along the gradient | Solid background |
| Link colour at 3:1 against body text only | Links hard to find | Links underlined, or 3:1 against surrounding text plus 4.5:1 against background |
| Input borders at 1.5:1 | Field edges invisible | Input border token at 3:1 against the surface |
| Focus ring in the same colour as the button fill | Invisible on the focused button | Focus token with 3:1 against both the control and the background; outline offset 2px |
| Icon-only buttons in light gray | Fails 3:1 for graphics | Icon colour at 3:1 minimum |
| Status badges with pale text on pale background ("light green on lighter green") | Common Tailwind badge pattern (`bg-green-100 text-green-500`) | Status text token darker (700–800 step) on the subtle background; check 4.5:1 |
| Disabled buttons that look active, or active buttons that look disabled | Grayed-out primaries confuse | Disabled uses a dedicated token pair and `cursor: not-allowed`; see part 18 |
| Contrast checked only in light mode | Dark theme fails silently | Check every token pair in both themes |
| Contrast "fixed" with `text-shadow` | Blurry and still failing | Change the colour |

## 12.5 Colour for meaning

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Colour as the only signal (red row = overdue, green dot = online) | Colour-blind users and grayscale printouts lose it | Colour plus text or icon: "Overdue" label, "Online" text |
| Status colours used as decoration (green header, red icon for "Hot deals") | Status loses meaning | Red, amber, green only for status |
| Red for "delete" buttons in every list row | Page looks like an alarm | Neutral row action; red only in the confirm step. See part 18 |
| Green for every money figure | Implies profit | Neutral for amounts. Green/red only for change (up/down) where direction matters, with a +/− sign |
| Negative numbers only in red with no minus sign | Colour-only meaning; prints wrong | `−₱500.00` or `(₱500.00)` plus red if DESIGN.md wants it |
| Red/green pair for pass/fail, up/down | Most common colour-blindness confusion | Pair with icons (✓/✕ as SVG) or text; choose blue/orange for charts when direction is the only difference |
| Warning yellow used for text | Unreadable on white | Warning icon and border in amber; text in a dark warning text token |
| Info blue identical to primary blue | Info messages look like buttons | Distinct info token, or neutral info style |
| Brand primary is red, and error is also red | Errors blend with brand | Error token different enough in hue or pair errors with icon and text |
| "Live" or "Online" dot in green with glow | See part 10 and part 01 | Flat dot plus text |
| Party colours for election candidates chosen by the model | Implies affiliation | Neutral colour for all candidates unless the client provides official party colours for a neutral results page. See part 09 |

## 12.6 Status colour tokens

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Status colours picked per component (`text-green-500` here, `#22c55e` there, `emerald-600` elsewhere) | Three greens for "success" | One token set per status: `--color-success`, `--color-success-text`, `--color-success-subtle`, same for warning, danger, info |
| More than 4 status hues | Users cannot learn them | success, warning, danger, info. Neutral for "draft", "archived", "inactive" |
| Pending shown in purple, "processing" in pink | Invented status hues | Neutral or info for in-progress states; the word carries the meaning |
| Gradient badges (`from-green-400 to-emerald-600`) | Decoration on metadata | Solid subtle background + status text token |
| Solid saturated badge fills everywhere (`bg-green-500 text-white`) | Loud tables | Subtle background with darker text; solid fill only for the one status that needs attention |
| Status shown by row background colour across a whole table | Heavy; hard to read | Status column with a badge; row tint only for selected rows |
| POS order status colours differing between screens | Cashier confusion | One mapping in one file: `status → token`. Used by POS, kitchen display and admin |

## 12.7 Opacity-based colour systems

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| All tints made with opacity (`bg-primary/10`, `text-white/60`, `border-white/10`) | Colour changes with whatever is underneath; contrast unpredictable | Opaque semantic tokens for each tint |
| Text colour via opacity (`opacity: 0.6` on muted text) | Also fades icons, links and focus rings inside | Muted text token |
| `rgba(255,255,255,0.1)` borders in dark mode | Glass-edge look; disappears on some surfaces | Border token defined per theme |
| `--primary-rgb` channel variables for `rgba(var(--primary-rgb), .1)` | Workaround for an opacity system | `--color-primary-subtle` token. Or `color-mix()` defined once in `tokens.css`, not per component |
| Hover via `opacity: 0.8` on coloured buttons | Fades text below contrast | Hover token |
| Disabled via `opacity: 0.5` on the whole control | Can pass or fail unpredictably; icons fade too | Disabled token pair (background, text) plus `aria-disabled` or `disabled` |
| Overlays via stacked semi-transparent layers | Muddy colours | One overlay token for dialog backdrops |

Opacity is fine for: dialog backdrops (one token), skeleton shimmer, drag previews, and images fading in.

## 12.8 Semantic tokens

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Components reference primitives (`var(--blue-600)`, `var(--gray-200)`) | Theme changes mean editing every component | Components reference semantic tokens only (`--color-primary`, `--color-border`) |
| Semantic names that describe colour (`--color-purple-button`) | Still a primitive | Name by role: `--color-action`, `--color-danger`, `--color-surface` |
| Separate tokens per component for the same role (`--card-border`, `--table-border`, `--input-border-light`) | Duplicates drift | Shared role tokens; component tokens only when a component truly differs |
| Tokens with no dark-theme value | Dark mode half-works | Every semantic colour token defined in each theme |
| Hex values pasted in components next to tokens | Half-migrated | Grep for hex and `rgb(` outside `tokens.css`; replace |
| Token names from shadcn (`--muted-foreground`, `--accent-foreground`) used with different meanings than shadcn intends | Confusing when mixed with the library | Keep shadcn names if using shadcn and map them to DESIGN.md; otherwise use the project's own names |
| No `on-` colours (text on primary, text on danger) | White text assumed on every fill | `--color-on-primary`, `--color-on-danger` defined and checked |

Minimum semantic set, with values from DESIGN.md:

```css
/* Use: semantic colour tokens (values from DESIGN.md) */
:root {
  --color-bg: ; --color-surface: ; --color-surface-alt: ;
  --color-border: ; --color-border-strong: ;
  --color-text: ; --color-text-muted: ; --color-text-subtle: ;
  --color-primary: ; --color-primary-hover: ; --color-primary-subtle: ; --color-on-primary: ;
  --color-link: ; --color-focus: ;
  --color-success: ; --color-success-text: ; --color-success-subtle: ;
  --color-warning: ; --color-warning-text: ; --color-warning-subtle: ;
  --color-danger: ;  --color-danger-text: ;  --color-danger-subtle: ; --color-on-danger: ;
  --color-info: ;    --color-info-text: ;    --color-info-subtle: ;
  --color-disabled-bg: ; --color-disabled-text: ;
  --color-overlay: ;
  --color-selection: ;
}
```

```css
/* Banned: primitives and opacity in components */
.badge-paid { background: rgba(16, 185, 129, 0.1); color: #10b981; }
.btn { background: linear-gradient(135deg, #6366f1, #8b5cf6); color: #fff; }

/* Use: semantic tokens */
.badge-paid { background: var(--color-success-subtle); color: var(--color-success-text); }
.btn { background: var(--color-primary); color: var(--color-on-primary); }
```

## 12.9 Dark mode colour errors

Whether to ship dark mode, dark-by-default and theme toggles are in part 34. This table covers colour mistakes inside a dark theme.

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Dark theme made with `filter: invert(1) hue-rotate(180deg)` | Inverts photos, logos, charts | Redefine semantic tokens under the dark theme selector |
| Light-theme colours reused unchanged on dark (same primary, same status colours) | Saturated colours vibrate on dark; some fail contrast | Dark-theme values for primary and status tokens, usually lighter and less saturated; re-check contrast |
| Elevation shown with darker shadows on dark surfaces | Shadows barely show on dark | Raised surfaces one step lighter than the page |
| Pure black page with pure white cards | Harsh jumps | Near-black page, slightly lighter surfaces |
| Borders as `rgba(255,255,255,.1)` everywhere | Glass look | Border token per theme |
| Logos and illustrations made for light backgrounds shown on dark | Dark logo disappears | Dark-theme logo variant from the brand kit |
| Charts keep light-theme palette on dark | Lines too dark, gridlines too bright | Chart tokens per theme |
| Status subtle backgrounds as light pastels on a dark page | Bright blocks on dark | Dark-theme subtle tokens (dark tinted) with lighter status text |
| Dark theme defined with `dark:` classes on some components and not others | Half-dark screens | Tokens switch per theme; components need no `dark:` classes |
| Code blocks and embeds staying light in dark theme | Glare | Theme-aware code block tokens |
| `color-scheme` not set | Native controls (scrollbars, date inputs, selects) stay light | `color-scheme: light dark` on `:root`, or per theme |

## 12.10 Colour on images and brand assets

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Purple or brand-colour overlay on hero photos | Tinted template look | Photo as-is; text outside it. See part 10 |
| Duotone filter on team or event photos | Decoration; people look odd | Original photo |
| Logo recoloured to match the site accent | Brand misuse | Logo as supplied, or an official monochrome variant |
| Client logo on a background that fails 3:1 | Invisible logo | Background chosen for the logo, or the logo's alternate version |
| LGU seal placed on a coloured band that clashes with the seal colours | Official mark looks off | Seal on a neutral surface. See part 09 |
| Screenshots with a coloured glow behind them | Trope | Plain border |

## 12.11 Government, school and local palettes

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| LGU site in flag blue, red and yellow everywhere | Flag colours as decoration; every LGU looks the same | Palette from the LGU's seal or DESIGN.md. Flag colours only where the client asks |
| School site in the model's guess of school colours | Schools have established colours | Ask for the school colours and use them as DESIGN.md tokens; check contrast, darken for text use if needed |
| Barangay site in purple gradients from a SaaS template | Template leftover | Neutral palette with one accent from the barangay seal |
| Election data pages using red and blue for up and down | Reads as party colours | Neutral data colours; see 12.5 |
| Colour carrying meaning on forms meant to be printed (red required fields) | Many offices print on black-and-white printers | Text markers ("Required") and borders; test in grayscale print preview |
| Receipts and invoices designed in colour | Thermal printers print black only | Black on white. Emphasis with weight and rules, not colour. See part 09 |

## 12.12 Charts and data colour

Chart types and chart library defaults are in part 20. This table covers colour only.

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Chart.js or Recharts default palette (rainbow, or `#8884d8` purple) | Library default | Chart tokens from DESIGN.md: `--chart-1` … `--chart-6` |
| Rainbow palette for ordered data (months, age bands) | Hue has no order | Sequential palette: one hue, light to dark |
| Sequential palette for categories | Implies an order that does not exist | Categorical palette, 6 hues maximum, tested for colour blindness |
| Red/green for categories | Colour-blind confusion; red reads as bad | Blue/orange or other distinguishable pairs |
| Gradient area fills and glowing lines | Decoration | Solid line, fill at a single low-opacity token if any |
| 10+ series each with its own colour | Unreadable legend | Top 5 series coloured, rest grouped as "Other" in gray; or small multiples |
| Highlight colour not reserved | Nothing stands out | Gray for context series, accent for the one series that matters |
| Diverging data (above/below target) in a sequential palette | Midpoint lost | Diverging palette with a neutral midpoint |
| Legend order not matching series order | Hunting | Same order as lines or stacks; direct labels where possible |
| Chart colours fail 3:1 against the background | Lines vanish | Each series at 3:1 minimum against the plot background |
| Map choropleth in rainbow | Hue has no order | Sequential palette by value, with a legend showing bins |

## 12.13 Links, focus, selection and interactive states

| AI pattern | Why it reads as generated | Use instead |
|---|---|---|
| Links in the same colour as body text with no underline | Links invisible | `var(--color-link)` plus underline in body text |
| Links in accent colour and also buttons, headings and icons in the same colour | Unclear what is clickable | Accent reserved for interactive elements |
| Visited links styled identically to unvisited in long lists | Users re-open the same items | `:visited` colour token in content lists and search results |
| Hover darkens by a hard-coded amount in each component | Inconsistent | `--color-primary-hover` token, one per interactive colour |
| Active nav item shown only by colour | Colour-only meaning | Colour plus weight, indicator bar or `aria-current` styling |
| Selected table rows in accent colour at full strength | Text contrast breaks | `--color-primary-subtle` background with normal text |
| Focus ring colour differing per component | Inconsistent | One `--color-focus` token |
| Error borders red with no message | Colour-only | Border plus error text. See part 17 |

## 12.14 Check

- [ ] No indigo, violet, purple, pink or fuchsia defaults unless DESIGN.md chose them.
- [ ] No `#667eea → #764ba2`, purple-pink or sunset gradients anywhere.
- [ ] No cyan or neon green on black.
- [ ] No Tailwind palette names (`indigo-600`, `slate-500`) in components.
- [ ] One accent per viewport; accent used only for primary actions, active nav, links and focus.
- [ ] Icons share one neutral colour; no rainbow icon sets.
- [ ] No pastel category fills per card.
- [ ] One gray ramp; no mixing slate, zinc and gray.
- [ ] No pure `#000` backgrounds or pure `#fff` text on dark.
- [ ] Tinted backgrounds only when DESIGN.md asks.
- [ ] Every text token pair checked at 4.5:1 (3:1 for large text) in both themes.
- [ ] Muted text checked on every surface it appears on, not only on white.
- [ ] Input borders, icons and focus indicators at 3:1.
- [ ] Placeholder text carries no required information.
- [ ] Text on images sits on a tested scrim or beside the image.
- [ ] Colour is never the only signal: status, errors, required fields, online state all have text or icon.
- [ ] Status colours used only for status; four status hues maximum.
- [ ] Status badges use subtle background plus dark status text, checked at 4.5:1.
- [ ] No gradient badges.
- [ ] Money amounts neutral; direction shown with sign plus colour.
- [ ] No opacity-based tints for text, borders or hover; opaque semantic tokens instead.
- [ ] Components reference semantic tokens only; primitives live in one file.
- [ ] `on-` colours defined for every filled colour.
- [ ] No hex or `rgb()` outside `tokens.css`.
- [ ] Dark theme redefines tokens; no `filter: invert`.
- [ ] Dark theme uses adjusted primary and status values; contrast re-checked.
- [ ] `color-scheme` set so native controls match the theme.
- [ ] Logos and seals not recoloured; dark-theme logo variant used where needed.
- [ ] LGU and school palettes come from the seal or school colours, not the flag or the model's guess.
- [ ] Printable forms and receipts work in black and white.
- [ ] Chart palette from tokens; sequential for ordered data, categorical (6 max) for categories.
- [ ] No red/green-only chart pairs.
- [ ] Links underlined in body text; one focus colour across the app.
